## **Problem**

Disable Gradient Tracking (requires\_grad\_)

## **Trigger**

Use this when freezing model parameters or detaching specific parameters in-place during fine-tuning or transfer learning.

## **Snippet**

`import torch`  
`import torch.nn as nn`

`# Initialize a standard linear layer`  
`layer = nn.Linear(10, 5)`

`# Freeze layer parameters in-place to prevent gradient computation`  
`for param in layer.parameters():`  
    `param.requires_grad_(False)`

`x = torch.randn(2, 10)`  
`out = layer(x)`  
`print(f"Output requires grad: {out.requires_grad}")`

## **Minimal Notes**

The trailing underscore indicates an in-place mutation of the tensor's state. You cannot call requires\_grad\_(False) on a non-leaf tensor that was generated within a computation graph.

## **Common Bug**

**Issue:** RuntimeError: you can only change requires\_grad flags of leaf variables.

**Cause:** Calling .requires\_grad\_() on an intermediate tensor generated by upstream operations.

**Quick Fix:** Call .detach() on the intermediate tensor first before modifying gradient settings.

## **Official Documentation URL**

https://docs.pytorch.org/docs/stable/generated/torch.Tensor.requires\_grad\_.html

## **Problem**

Create Detached Tensor (torch.detach / detach\_)

## **Trigger**

Use this when extracting a tensor from the computation graph to stop gradient propagation without copying data.

## **Snippet**

`import torch`

`x = torch.randn(3, 3, requires_grad=True)`  
`y = x * 2`

`# Detach y from computation graph; detached tensor shares underlying storage`  
`y_detached = y.detach()`  
`loss = y_detached.sum()`

`print(f"y_detached requires_grad: {y_detached.requires_grad}")`  
`print(f"Shares storage: {y_detached.data_ptr() == y.data_ptr()}")`

## **Minimal Notes**

detach() returns a new view tensor that shares memory with the original tensor but has no gradient history. In-place modification of a detached tensor will affect the original tensor and trigger autograd errors if used in backward passes.

## **Common Bug**

**Issue:** RuntimeError: one of the variables needed for gradient computation has been modified by an inplace operation.

**Cause:** Modifying a detached tensor in-place while its parent tensor is required for autograd backward pass.

**Quick Fix:** Use .clone().detach() instead of .detach() when you plan to modify the detached data in-place.

## **Official Documentation URL**

https://docs.pytorch.org/docs/stable/generated/torch.Tensor.detach.html

## **Problem**

Enable Gradient Calculation Context (torch.enable\_grad)

## **Trigger**

Use this to locally re-enable gradient calculation inside a torch.no\_grad() or torch.inference\_mode() block.

## **Snippet**

`import torch`

`x = torch.randn(2, 2, requires_grad=True)`

`with torch.no_grad():`  
    `# Gradients disabled here`  
    `intermediate = x * 2`  
      
    `with torch.enable_grad():`  
        `# Gradients re-enabled locally for fine-tuning or adversarial steps`  
        `y = intermediate * 3`  
        `loss = y.sum()`  
        `loss.backward()`

`print(f"Gradient on x: {x.grad}")`

## **Minimal Notes**

torch.enable\_grad can be used as a context manager or decorator to enforce gradient calculation. It operates thread-locally and does not impact autograd tracking in other running threads.

## **Common Bug**

**Issue:** Tensor.grad remains None after calling .backward().

**Cause:** Creating input tensors inside torch.no\_grad() before entering torch.enable\_grad(), causing intermediate tensors to lack graph connectivity.

**Quick Fix:** Ensure input tensors have requires\_grad=True prior to entering the gradient-tracked section.

## **Official Documentation URL**

https://docs.pytorch.org/docs/stable/generated/torch.enable\_grad.html

### **Backward Pass**

## **Problem**

Compute Gradients (Tensor.backward)

## **Trigger**

Use this to trigger automatic backpropagation from a scalar loss tensor to compute gradients for all leaf parameters.

## **Snippet**

`import torch`

`weights = torch.randn(3, 3, requires_grad=True)`  
`inputs = torch.randn(3, 3)`

`# Forward pass computing scalar loss`  
`loss = (weights @ inputs).sum()`

`# Compute gradients with respect to leaf tensors`  
`loss.backward()`

`print(f"Calculated gradient:\\n{weights.grad}")`

## **Minimal Notes**

If calling backward() on a non-scalar tensor, you must supply a gradient argument matching the tensor shape. Calling backward() frees graph buffers unless retain\_graph=True is specified.

## **Common Bug**

**Issue:** RuntimeError: grad can be implicitly created only for scalar outputs.

**Cause:** Calling .backward() without arguments on a non-scalar tensor.

**Quick Fix:** Pass a matching weighting tensor, e.g. loss.backward(torch.ones\_like(loss)), or reduce the tensor to a scalar using .sum().

## **Official Documentation URL**

https://docs.pytorch.org/docs/stable/generated/torch.Tensor.backward.html

## **Problem**

Compute Gradients with torch.autograd.backward

## **Trigger**

Use this to compute vector-Jacobian products across multiple output tensors or customized gradient targets simultaneously.

## **Snippet**

`import torch`

`x = torch.randn(3, requires_grad=True)`  
`y = x * 2`  
`z = x * 3`

`# Compute sum of vector-Jacobian products for multiple root outputs`  
`grad_tensors = [torch.ones_like(y), torch.ones_like(z)]`  
`torch.autograd.backward([y, z], grad_tensors=grad_tensors)`

`print(f"Accumulated gradient on x: {x.grad}")`

## **Minimal Notes**

torch.autograd.backward accumulates gradients directly into .grad attributes of specified graph leaves. The lengths of tensors and grad\_tensors must match exactly unless output elements are scalar.

## **Common Bug**

**Issue:** RuntimeError: Mismatch in length of tensors and grad\_tensors.

**Cause:** Passing a list of output tensors to torch.autograd.backward with a non-matching number of gradient weight tensors.

**Quick Fix:** Provide a matching grad\_tensors list containing one tensor per output tensor.

## **Official Documentation URL**

https://docs.pytorch.org/docs/stable/generated/torch.autograd.backward.html

### **Graph Control**

## **Problem**

Retain Computation Graph (retain\_graph)

## **Trigger**

Use this when you need to execute multiple backward passes through the same computation graph, such as in multi-task loss optimization.

## **Snippet**

`import torch`

`x = torch.randn(2, 2, requires_grad=True)`  
`shared = x * 3`

`loss1 = shared.sum()`

`loss1.backward(retain_graph=True)`

## **Minimal Notes**

retain\_graph=True prevents autograd from freeing intermediate activation buffers after backpropagation. Holding graph buffers increases peak GPU memory usage significantly across iterations.

## **Common Bug**

**Issue:** RuntimeError: Trying to backward through the graph a second time (or directly access saved variables).

**Cause:** Calling backward() multiple times on a graph without setting retain\_graph=True on earlier calls.

**Quick Fix:** Set retain\_graph=True on all backward() calls except the final one.

## **Problem**

## **Trigger**

        `(x,) = ctx.saved_tensors`

`# Execute custom function via .apply()`

Always invoke custom functions via Function.apply(\*inputs) rather than calling forward() directly. Use ctx.save\_for\_backward(\*tensors) to stash intermediate tensors required during backward computation.

## **Common Bug**

**Issue:** Memory leaks or incorrect autograd graph construction when calling custom autograd functions.

**Cause:** Calling CubeFunction.forward(x) directly instead of CubeFunction.apply(x).

**Quick Fix:** Always use CustomFunction.apply(...) to execute forward and register the backward pass.
