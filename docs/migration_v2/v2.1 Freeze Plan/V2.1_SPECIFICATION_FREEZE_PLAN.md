# AENS v2.1 Specification Freeze Plan

**Date:** 2026-06-30
**Purpose:** Resolve genuine contradictions and fill highest-value missing contracts to enable AI coding agent implementation
**Target:** 1-2 focused days of specification work
**Baseline:** v2.0 architecture documents (8 documents in `docs/migration_v2/`)

---

# Executive Summary

The v2.0 architecture has a strong conceptual foundation (7.8-8.5/10) but contains ~6-7 truly critical blockers that would force AI agents to make architectural decisions during implementation. This document provides a focused plan to resolve these blockers through concrete design decisions rather than additional analysis.

**Philosophy:** This freeze prioritizes resolving contradictions and undefined contracts over adding new features. The goal is to make the specification complete enough for AI agents to implement without invention, not to perfect every aspect of the design.

**Key Principle:** Follow the canonical authority philosophy. Expand existing governing documents rather than creating new ones. Specify behavior rather than implementation details.

# Must Fix Before Implementation (Highest Priority)

These are physical impossibilities, direct contradictions, or undefined contracts that would block implementation entirely.

## Fix 1: JS ↔ TS Execution Model

**Issue:** Scripts specified as `.js` files (`node scripts/validate.js`) but must import `.ts` modules. Node.js cannot directly import TypeScript without transpilation.

**Affected Documents:**
- `BUILD_PIPELINE_SPECIFICATION.md` (package.json scripts)
- `FOUNDATION_IMPLEMENTATION_BLUEPRINT.md` (script imports)
- `IMPLEMENTATION_SPECIFICATION.md` (script dependencies)

**Resolution Decision:**
- **Approach:** Use `tsx` as the TypeScript execution runtime for all scripts
- **Script files:** Rename all `.js` scripts to `.ts` (validate, build-nav, build-search-index, etc.)
- **package.json commands:** Update all script invocations to use `tsx`
  ```json
  "validate": "tsx scripts/validate.ts"
  "validate:all": "tsx scripts/validate.ts --all"
  "build-nav": "tsx scripts/build-nav.ts"
  "build-search-index": "tsx scripts/build-search-index.ts"
  ```
- **Dev dependency:** Add `tsx` to `package.json` devDependencies
- **Documentation update:** Update `BUILD_PIPELINE_SPECIFICATION.md` to reflect `tsx` usage

**Rationale:** `tsx` is the modern, zero-config TypeScript executor. It requires no build step and works seamlessly with ESM. This is the simplest path forward for a TypeScript-first project.

## Fix 2: Loader vs Validator Contradiction

**Issue:** Module isolation rules state "Loader MUST NOT import validation logic" but `loadContentFile()` specification requires "Validate against appropriate schema" with dependency on `lib/validation/layer1-schema.ts`.

**Affected Documents:**
- `IMPLEMENTATION_SPECIFICATION.md` (Module Isolation Rules vs. Function Specifications)

**Resolution Decision:**
- **Approach:** Pure loader (Option 2)
- **Loader behavior:** `loadContentFile()` is a pure file reader. It parses JSON and returns the raw object. No validation.
- **Validation responsibility:** All validation is performed exclusively by the build-time validation pipeline (`scripts/validate.ts`)
- **Module isolation:** Enforce `lib/content/` → NO imports from `lib/validation/`
- **Update required:**
  - Remove "Validate against appropriate schema" from `loadContentFile()` specification
  - Remove `lib/validation/layer1-schema.ts` from `loadContentFile()` dependencies
  - Add note: "Validation is performed by the validation pipeline, not the loader"

**Rationale:** This is architecturally cleaner. The build pipeline runs validation before rendering. The loader should be a pure data access layer. This also aligns with the "build-time verification" principle.

## Fix 3: Phase Ordering Inconsistency

**Issue:** `FOUNDATION_IMPLEMENTATION_BLUEPRINT.md` has Phase 5 (Validation) before Phase 6 (Metadata), but Layer 4 semantic validation requires metadata files that don't exist until Phase 6. Circular dependency.

**Affected Documents:**
- `FOUNDATION_IMPLEMENTATION_BLUEPRINT.md` (Phases 5 and 6)
- `REBUILD_PHASE_CHECKLIST.md` (already has correct order)
- `AENS_REBUILD_MASTER_PLAN.md` (already has correct order)

**Resolution Decision:**
- **Swap phases in blueprint:** Change `FOUNDATION_IMPLEMENTATION_BLUEPRINT.md` to:
  - Phase 5: Metadata (was Phase 6)
  - Phase 6: Validation (was Phase 5)
- **Update dependency graph:**
  ```
  Phase 5 (Metadata) ← depends on Phase 3
      ↓
  Phase 6 (Validation) ← depends on Phase 2, 3, 4, 5
  ```
- **Validation dependency:** Layer 4 explicitly depends on Phase 5 metadata files
- **Consistency check:** Verify phase numbering matches `REBUILD_PHASE_CHECKLIST.md` and `AENS_REBUILD_MASTER_PLAN.md`

**Rationale:** Metadata must exist before semantic validation can run. The other two documents already have the correct order; the blueprint is the outlier.

## Fix 4: Content Schema Internal Structures

**Issue:** Schema specifications list required field names but not their internal shapes (e.g., `Model.architecture`, `Package.common_tasks`, `Workflow.steps`). AI agents must invent these structures.

**Affected Documents:**
- `REPOSITORY_FOUNDATION_SPECIFICATION_v2.md` (Content Model)
- `FOUNDATION_IMPLEMENTATION_BLUEPRINT.md` (Phase 3)

**Resolution Decision:**
- **Expand existing authority:** Add complete content type definitions to `REPOSITORY_FOUNDATION_SPECIFICATION_v2.md` (do NOT create a new document)
- **Define complete shapes for all nested objects within the Content Types section:**
  - `Package.common_tasks`: Array of `{ task: string, priority?: 'high' | 'medium' | 'low' }`
  - `Model.architecture`: Object with `{ layers: string[], parameters: number, type: string }`
  - `Model.evaluation`: Object with `{ metrics: { [key: string]: number }, dataset: string }`
  - `Model.decision_guide`: Object with `{ when_to_use: string[], when_to_avoid: string[], alternatives: string[] }`
  - `Workflow.steps`: Array of `{ title: string, description: string, code?: string }`
  - `Workflow.prerequisites`: Object with `{ confirmed_env: string[], required_packages: string[] }`
  - `Workflow.production_notes`: Object with `{ performance: string, scaling: string, monitoring: string }`
  - `Registry.deployment`: Object with `{ provider: string, region: string, config: object }`
  - `Registry.hardware_requirements`: Object with `{ gpu?: string, memory: string, cpu: string }`
  - `Cheatsheet.entries`: Array of `{ syntax: string, description: string, example: string }`
- **Include constraints:** Required vs optional, maxLength, maxItems, patterns
- **Add examples:** Provide example values for each field
- **JSON Schema generation:** These shapes become the basis for actual `schema/v2/*.json` files
- **Update canonical authority table:** Ensure `REPOSITORY_FOUNDATION_SPECIFICATION_v2.md` remains the single source of truth for content type definitions

**Rationale:** This is the single most important missing specification. Without defined shapes, JSON Schema files cannot be written, TypeScript types cannot be generated, and validation cannot function. Expanding the existing canonical authority document prevents drift and follows the single-source-of-truth principle.

## Fix 5: Deterministic Navigation Ordering

**Issue:** `_nav.json` generation uses `fs.readdir()` which has non-deterministic order across platforms. Violates deterministic generation invariant.

**Affected Documents:**
- `IMPLEMENTATION_SPECIFICATION.md` (scripts/build-nav.js)
- `REPOSITORY_FOUNDATION_SPECIFICATION_v2.md` (Deterministic Generation principle)

**Resolution Decision:**
- **Sorting rule:** Sort navigation items by:
  1. `title` ascending (alphabetical)
  2. `id` ascending (as tiebreaker)
- **Implementation:** Update `build-nav.js` algorithm to explicitly sort before writing `_nav.json`
- **Documentation:** Add to `IMPLEMENTATION_SPECIFICATION.md`: "Sort items by title ascending, then by id ascending to ensure deterministic generation across platforms"
- **Validation:** Add test that verifies `_nav.json` is sorted correctly

**Rationale:** Deterministic builds are a core principle. Platform-dependent ordering causes unnecessary git diffs and merge conflicts.

## Fix 6: Package.json Build Script Mismatch

**Issue:** Written spec for production build includes type-check and lint, but package.json `build:prod` script only includes validate and build-artifacts.

**Affected Documents:**
- `BUILD_PIPELINE_SPECIFICATION.md` (Production Build specification)
- package.json (scripts section)

**Resolution Decision:**
- **Update package.json script:**
  ```json
  "build:prod": "pnpm type-check && pnpm lint && pnpm validate:all && pnpm build-artifacts && next build"
  ```
- **Add missing scripts if not present:**
  ```json
  "type-check": "tsc --noEmit",
  "lint": "eslint . --ext .ts,.tsx"
  ```
- **Documentation consistency:** Verify `BUILD_PIPELINE_SPECIFICATION.md` matches this sequence

**Rationale:** Specs and code must match. Otherwise documentation drifts immediately and CI will behave differently than documented.

# Should Fix Before Implementation

These are not absolute blockers but should be resolved to prevent architectural drift or confusion.

## Fix 7: Category Assignment Algorithm

**Issue:** Navigation generator assigns categories "based on tags" but no mapping exists from tags to categories in `metadata/categories.json`.

**Affected Documents:**
- `IMPLEMENTATION_SPECIFICATION.md` (scripts/build-nav.js)
- `REPOSITORY_FOUNDATION_SPECIFICATION_v2.md` (Metadata System)

**Resolution Decision:**
- **Approach:** Tags-based inference with explicit rules in metadata
- **Keep content semantic:** Do NOT add `category` to BaseMeta. Content should contain semantic tags, not presentation categories.
- **Expand metadata/categories.json:** Add tag-to-category mapping rules:
  ```json
  {
    "id": "ml",
    "display_name": "Machine Learning",
    "content_types": ["model", "package"],
    "tag_rules": {
      "required_tags": ["ml", "machine-learning"],
      "priority": ["ml", "dl", "llm"]
    }
  }
  ```
- **Assignment algorithm:** For each content item, find the category whose `tag_rules.priority` array contains the most matching tags from the item's `tags` array. If tie, use first matching category. If no match, assign "uncategorized" and emit validation warning.
- **Rationale:** Categories are presentation/navigation concerns, not content semantics. Keeping tags in content and category rules in metadata allows navigation to evolve without touching thousands of content files. This is more scalable for long-term maintenance.

## Fix 8: Search Behavior Specification

**Issue:** `lib/search/engine.ts`, `inverted-index.ts`, `related-search.ts` are in directory structure but have no API specifications. Search is a core user-facing feature.

**Affected Documents:**
- `REPOSITORY_FOUNDATION_SPECIFICATION_v2.md` (Directory Structure)
- `FOUNDATION_IMPLEMENTATION_BLUEPRINT.md` (Phase 8)

**Resolution Decision:**
- **Specify behavior, not implementation:** Define search capabilities and requirements without binding to specific libraries
- **Required search behaviors:**
  - Fuzzy text matching (tolerant of typos, partial matches)
  - Alias search (search by alternative names)
  - Tag search (filter by tag, search within tagged content)
  - Keyword search (search within keyword fields)
  - Ranked output (results ordered by relevance score)
  - Field-weighted ranking (title > aliases > tags/keywords > description)
- **API specification:**
  ```typescript
  interface SearchEngine {
    search(query: string, options?: SearchOptions): SearchResult[]
  }
  interface SearchOptions {
    limit?: number
    category?: string
    contentType?: string
    tags?: string[]
  }
  interface SearchResult {
    id: string
    type: string
    title: string
    score: number  // 0-1, higher is better
  }
  ```
- **Implementation guidance:** The current implementation uses fuse.js. Future implementations may use different libraries. The architecture should specify behavior, not library configuration.
- **Clarify `inverted-index.ts` and `related-search.ts`:** If these files are not needed for the specified behavior, remove them from the directory structure. If they are needed, specify their behavioral purpose (e.g., "inverted-index.ts provides O(1) tag-based lookup").

**Rationale:** Search is a primary user interaction point. Behavior-focused specification allows the implementation to evolve (e.g., switching from fuse.js to a different library) without requiring architecture document updates.

## Fix 9: .gitignore Clarification

**Issue:** `search-index.json` is specified as "Committed: Yes, Gitignored: When in development mode only" — a contradiction. A file cannot be both tracked and gitignored.

**Affected Documents:**
- `BUILD_PIPELINE_SPECIFICATION.md` (Artifact Management)

**Resolution Decision:**
- **Approach:** Commit all artifacts, never gitignore
- **Decision:** `search-index.json` and `_nav.json` are always committed to git
- **No .gitignore entries:** Do not add these files to `.gitignore`
- **Rationale:** For a static site, committed artifacts ensure deterministic builds and simple deployment. Development mode should use the same artifact generation as production.
- **Documentation update:** Change "Gitignored: When in development mode only" to "Gitignored: Never"

**Alternative (if development gitignore is desired):**
- Use build-time detection: if `process.env.NODE_ENV === 'development'`, skip artifact generation
- But this breaks the "deterministic builds" principle

## Fix 10: Model ID Strategy

**Issue:** Model IDs use `model:transformer` format but models are in subdirectories (`ml/`, `dl/`, `llm/`). Resolver cannot determine which subdirectory. Potential ID collisions.

**Affected Documents:**
- `REPOSITORY_FOUNDATION_SPECIFICATION_v2.md`
- `FOUNDATION_IMPLEMENTATION_BLUEPRINT.md`
- `IMPLEMENTATION_SPECIFICATION.md`

**Resolution Decision:**
- **Approach:** Explicit deterministic ID policy (no recursive search)
- **Policy choice:** Encode category in the ID: `model:ml:transformer`, `model:dl:transformer`, `model:llm:transformer`
- **ID format:** `{type}:{category}:{slug}` for models only (other content types remain `{type}:{slug}`)
- **Validation:** Layer 2 validation enforces that model IDs follow this format and that the category matches the actual subdirectory
- **Resolver behavior:** `resolveById("model:ml:transformer")` constructs path as `content/models/ml/transformer.json` (deterministic, no search)
- **Documentation:** Add to `REPOSITORY_FOUNDATION_SPECIFICATION_v2.md`: "Model IDs use format `model:{category}:{slug}` where category is one of: ml, dl, llm"
- **Alternative (if encoding is rejected):** Require global slug uniqueness across all model subdirectories and document as invariant. Resolver would need to search subdirectories, but this is less deterministic.

**Rationale:** Explicit encoding in the ID is deterministic and requires no search. The category is already implicit in the directory structure; making it explicit in the ID removes ambiguity. Recursive search hides problems and is unnecessary magic.

## Fix 11: Schema Evolution Policy

**Issue:** The architecture supports schema versioning (`schema/v2`, `schema/v3`) but does not define when a new schema version should be created vs. when compatible changes can be made to the existing version.

**Affected Documents:**
- `REPOSITORY_FOUNDATION_SPECIFICATION_v2.md` (Configuration)
- `FOUNDATION_IMPLEMENTATION_BLUEPRINT.md` (Schema)

**Resolution Decision:**
- **Create new section:** Add "Schema Evolution Policy" to `REPOSITORY_FOUNDATION_SPECIFICATION_v2.md`
- **Define compatible changes (do NOT require new schema version):**
  - Adding optional fields to existing content types
  - Adding new content types
  - Relaxing constraints (e.g., increasing maxLength, expanding enum values)
  - Adding new validation rules that are warnings, not errors
- **Define breaking changes (require new schema version):**
  - Removing or renaming required fields
  - Changing field types
  - Tightening constraints (e.g., decreasing maxLength, restricting enum values)
  - Changing the structure of nested objects
  - Removing content types
- **Migration rules:** When creating v3, specify migration path from v2 to v3
- **Deprecation rules:** Fields can be marked deprecated in current version before removal in next version
- **Version lifecycle:** Support at most 2 active schema versions at any time. When v3 is released, v1 is deprecated.

**Rationale:** Without an evolution policy, future maintainers will be uncertain whether a change requires a new schema version. This prevents schema version sprawl and provides clear guidance for architectural decisions.

# Success Criteria

The v2.1 specification freeze is complete when:

1. **No physical impossibilities:** All scripts can execute as specified
2. **No contradictions:** No document states X while another states not-X
3. **No undefined contracts:** Every function, module, and data structure has complete specification
4. **Deterministic behavior:** All generation algorithms have explicit ordering rules
5. **Behavior over implementation:** Specifications describe what, not how (e.g., search behavior, not fuse.js config)
6. **Single source of truth:** No new governing documents created; existing authorities expanded
7. **AI agent implementability:** An AI agent can implement any phase without making architectural decisions
