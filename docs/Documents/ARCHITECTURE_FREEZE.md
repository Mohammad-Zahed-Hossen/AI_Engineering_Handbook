# Purpose

This document captures the architectural decisions made for AENS (AI Engineering Handbook). The architecture is now frozen and will not be changed without explicit justification and review.

---

# Scope

**Maximum Expected Resources:** ~200 canonical resources

**Nature:** Curated engineering knowledge base (not a documentation platform)

**Target Audience:** AI engineers seeking canonical implementation knowledge

---

# Architectural Decisions

## Storage

**Format:** JSON files in `data/` directory  
**Structure:** Flat directory structure per content type  
**Rationale:** Simple, human-readable, version-controllable. 200 files per directory is well within file system limits.

---

## Search

**Engine:** Fuse.js (fuzzy search) + custom inverted index  
**Architecture:** Client-side indexing with React cache  
**Rationale:** For ~2,800 searchable items (200 content + ~2,000 package tasks + ~600 cheatsheet entries), Fuse.js provides <10ms response time with ~100-200KB memory. No enterprise infrastructure needed.

**Rejected Alternatives:**
- Elasticsearch (overkill for 200 resources)
- Typesense (overkill for 200 resources)
- Meilisearch (overkill for 200 resources)
- Vector search (not needed for this scope)

---

## Knowledge Graph

**Relationships:** Bidirectional only  
**Validation:** Automated enforcement in validate-content.ts  
**Rationale:** Knowledge graph integrity is critical. If `A → uses → B` exists, then `B → used_by → A` must exist. This is enforced as an ERROR in validation.

**Relationship Types:** 14 typed relationships (uses, implements, requires, depends_on, alternative_to, extends, built_with, optimized_by, benchmarked_by, debugged_by, deployed_with, references, supersedes, related_to)

---

## Knowledge Ownership

**Content Types and Their Owned Knowledge:**

- **Package:** Owns implementation knowledge (how to implement X with library Y)
- **Model:** Owns algorithm knowledge (which algorithm to use)
- **Workflow:** Owns process knowledge (how to build X end-to-end)
- **Cheatsheet:** Owns syntax recall (what's the syntax again?)
- **Pattern:** Owns concept knowledge (engineering concepts and best practices)
- **Debug Guide:** Owns troubleshooting knowledge (how to fix X error)
- **Decision Guide:** Owns decision knowledge (X vs Y, which to choose)
- **Principle:** Owns principle knowledge (engineering principles and axioms)
- **Registry:** Owns asset listing (models, datasets, services)
- **Problem Index:** Owns problem categorization (discovery layer only, no knowledge)

**Non-Ownership Rule:** Navigation views never own knowledge. They are dynamically generated from the content graph.

---

## Navigation

**Architecture:** Generated from content graph  
**Primary Entry Points:** Global Search, Sidebar Navigation, Problem Index, Dashboard, Recent Activity, Favorites, Collections, Continue Reading, Related Content, Cross References

**Implementation:** Lightweight `_nav.json` files for sidebar navigation, generated by `build-nav-index.ts`

---

## Schemas

**Schema Engine:** Zod  
**Base Schema:** BaseMetaSchema (shared across all content types)  
**Validation:** Required before commit (npm run validate)

**Schema Evolution:** migrate-to-v2.ts script was executed for AENS v2 model schema migration. The Model schema was subsequently extended to support optional `quickstart` code blocks and `learning_resources` curated references. Schema versioning is defined in aens.config.json. In version 1.2, the visual presentation layer of the Model detail pages was refactored for premium UX (incorporating a semantic decision strip, separated explainability block, unified 2x2 tradeoffs grid, 3-column complexity specs sheet, side-by-side comparative hyperparameters layout, and VS alternatives cards).

---

## Validation

**Pipeline:** validate-content.ts  
**Required:** Yes (prebuild hook enforces this)  
**Checks:**
- JSON parse errors
- Schema validation
- Slug format validation
- Filename/ID consistency
- Placeholder detection
- Minimum content quality
- Duplicate detection
- Reference integrity (broken links)
- **Bidirectional relationship integrity (ERROR)**
- docs_url uniqueness
- Duplicate URL checks (across sources and learning resources)
- Legacy ratings checks (replaces speed/memory rating enums with difficulty and maturity)

---

## Content Creation

**Rules:**
- Cannot violate ownership rules
- Must pass all validation checks
- Bidirectional relationships required
- Must follow content quality standard (see CONTENT_QUALITY_STANDARD.md)

---

## Problem Index

**Architecture:** Generated navigation structure  
**Schema:** None (per specification)  
**Data:** `data/problem-index/taxonomy.json`  
**Purpose:** Primary discovery layer for problem-first navigation  
**Implementation:** Static JSON taxonomy + page route

---

## Build Pipeline

**Framework:** Next.js 16.2.9 with static generation  
**Build Time:** ~30-40s for 200 files (acceptable for curated knowledge base)  
**Prebuild Hooks:** validate + build:nav

**Rejected Alternatives:**
- Incremental build system (not needed for 200 resources)
- Parallel build optimization (not needed for this scope)

---

## Repository Organization

**Structure:** Flat directories per content type  
**Example:** `data/packages/*.json`, `data/models/dl/*.json`  
**Rationale:** 200 files per directory is manageable. No sharding needed.

**Rejected Alternatives:**
- Directory sharding (a-z organization) (not needed for 200 resources)
- Content type-specific subdirectories (adds complexity without benefit)

---

## Caching

**Strategy:** React cache() for data loaders (per-request cache)  
**Rationale:** For 200 resources, disk I/O is acceptable. No persistent caching layer needed.

**Rejected Alternatives:**
- Redis (overkill for 200 resources)
- CDN integration (not needed for this scope)

---

## Technology Stack

**Framework:** Next.js 16.2.9  
**Language:** TypeScript  
**Schema Validation:** Zod  
**Search:** Fuse.js  
**Styling:** Tailwind CSS  
**UI Components:** shadcn/ui + Radix UI  
**Icons:** Lucide React

---

## What We Will NOT Do

**Rejected Infrastructure (solves problems we will never have):**
- Elasticsearch
- Typesense
- Meilisearch
- Redis
- Vector database
- Incremental build system
- Directory sharding
- Plugin architecture
- Dynamic schema loading
- Event bus
- CQRS
- Repository pattern
- Domain-driven architecture

**Rationale:** These solve problems for thousands of resources. AENS is a curated knowledge base of ~200 canonical resources. Simplicity is preferred over enterprise architecture.
